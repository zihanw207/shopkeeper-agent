# 独立测试集 v1

这是面向当前问数 Agent 的**候选保留测试集**：46 个场景、63 轮输入，绑定 `warehouse-extension-v1`（2024—2025 年，9,840 笔订单）。题目用于检验业务计算、澄清、分析证据和多轮状态；参考答案不会进入请求、提示词或检索库。

截至 2026-09-19，完成了参考答案验证，**没有运行这套题的真实模型评测，也没有准确率成绩**。57 条参考查询在内存 SQLite 与本机 MySQL 上结果一致；18 条能执行但业务逻辑有误的 SQL 变体，在两个数据库上均能与正确答案区分。另有自动化测试检查判分器和会话采集器。这些数字是测试集质量检查，不是 Agent 的通过率。

## 内容与难点

| 类别 | 场景数 | 主要覆盖 |
| --- | ---: | --- |
| 查数 | 28 | 跨年环比、闰年自然日、加权均值、跨月去重、复购队列、分区排名、并列档位、Top-K 分母、累计和滚动窗口、NULL、补零、真实空结果 |
| 行为选择 | 6 | 指标分母不明确、比较基准缺失、没有退款或广告数据、拒绝修改和越权读取 |
| 结果分析 | 4 | 纠正错误下降前提、品类变动贡献、区分客户数量与客单价、合并指标的权重、承认数据不完整 |
| 多轮状态 | 8 | 去掉筛选、替换指标和年份、澄清后继续、切换话题、环比改同比、A/B 会话隔离、拒绝请求后保留成功上下文 |

完整题目见 [questions.md](questions.md)。机器可读定义见 [cases.json](cases.json)，参考结果见 [goldens.json](goldens.json)，版本与摘要见 [manifest.json](manifest.json)。每个问题都带预期终态、评分要点和严重错误说明。分析题包含多组参考数据，允许 Agent 使用等价查询及不同分析路径。

大部分题目的设计难点在计算口径和上下文组合，另有少量空结果、拒绝请求等边界控制题。`difficulty` 是出题时的估计，不代表已经测得模型难度。

例如：

- **HSQL12**：先取销售额前三商品，再计算它们占整个地区全年金额的比例。若分母也只算前三名，SQL 合法但答案错误。
- **HSQL15**：只展示 4—6 月，年内累计仍从 1 月开始。过早过滤月份会低估累计值。
- **HSQL18**：跨月合并时既有 NULL 金额又有不同订单数，已知金额平均值要用金额已知的订单作为分母。
- **HA01**：问题声称销售额下降，数据实际上涨。回答必须先纠正前提。
- **HM01**：先取消品牌，再取消地区，并把分母改成客户数；旧筛选不能悄悄遗留。
- **HM07**：A 问完后，B 只问“那华南呢”。B 必须澄清，不能借用 A 的时间和指标。

## 独立性和使用边界

这套问题未用来调整当前生产提示词。原有 12 道种子题、2 个多轮冒烟场景、7 个数据扩充演示继续作为开发集，不计入本集成绩。

不过，**本集与开发演示共享表结构和数据快照**。其中 23 个场景标记为 `background_holdout`，17 个场景是已知边界数据上的新组合 `compositional_transfer`，6 个为 `behavior_holdout`。这些标签应分开报告；不能将它称为全新数据库泛化评测或完全未见数据测试。

扩充数据为合成数据，原始 2025 Q1 样例较稀疏，客户规模只有 20 人。跨年比较可验证计算，不能拿来证明真实经营原因。该集也不测大规模数据库性能、真实退款漏斗、真实因果识别或长历史记忆。

首次模型运行前已冻结题目、答案和数据摘要。运行时只校验，**不会按当前数据库重新生成正确答案**；数据变化会停止评测。若参考定义有错误，应记录勘误并升级版本，不能根据被测模型输出悄悄改答案。若开始根据本集失败题调参或改提示词，应把相应题目转为回归开发题，并为最终对比另建保留集。

### 已观察并用于修复的题目

2026-09-20：用户在网页上试测 **HSQL07**，模型生成了正确的相关 `NOT EXISTS` 查询，但应用的函数允许列表漏掉 SQLGlot 归类为 `Func` 的 `EXISTS`，因此被策略检查拒绝，未进入数据库执行或 SQL 修复。本次补齐允许项，并增加子查询语义及安全边界回归测试；未改变提示词、冻结题目或答案。原始 SQL 在真实 MySQL 上只读回放，返回 C011—C020 共 10 位客户，与参考答案一致；没有重新调用模型。这是确定性 SQL 回放验证，不是修复后的端到端模型成绩。

**HSQL07 从此作为已曝光的回归题，后续独立保留题成绩应剔除它或单列。** 为保留原始版本，机器定义和采集器的 `--all` 仍包含该题；正式汇总须依据本节排除。按此记录剔除后，候选保留场景为 45 个；其中常规在线采集范围为 42 个场景、57 轮，其余为隔离测试题。前述 46 / 63 和在线 43 / 58 是原始全集规模。

## 如何运行

在项目根目录执行。以下两个命令均不调用模型、不修改业务数据：

```bash
# 默认行为也是离线核对：版本、57 条参考查询、18 条错误变体
uv run python -m app.scripts.evaluate_holdout --check-fixture

# 在只读事务中核对本机 MySQL 的完整数据与参考结果
uv run python -m app.scripts.evaluate_holdout --check-database
```

在线采集需先启动现有后端及依赖服务，会产生真实模型调用。建议先固定模型、提示词、数仓、检索索引版本，另用开发集检查服务连通，再一次性运行保留题。以下是**运行入口，不表示本次已执行**：

```bash
# 必须显式选择完整场景；--case 可重复指定
uv run python -m app.scripts.evaluate_holdout --run-online --case HSQL12 --case HM07

# 完整普通场景：43 个场景、58 轮；其余 3 场景、5 轮标为 not_run
uv run python -m app.scripts.evaluate_holdout --run-online --all
```

`HB05`、`HB06`、`HM08` 标为 `mock_only`。采集器直接跳过，不向当前数据库权限配置下的服务发送这些请求。它们留给替换数据库执行器的测试环境；单元测试已确认采集器不会发送这类题。当前未提供这 3 个场景的真实模型隔离执行器，不能把跳过写成“已通过安全测试”。

每个场景新建会话，每个 lane 使用独立会话；多轮题按顺序完整运行。HM07 测试**交错请求下的上下文隔离**，不代表压力测试或 A/B 同时执行的并发验证。单轮题也携带会话 ID，与网页使用的澄清路径一致。

报告默认写入 `evals/reports/holdout-v1/` 的新文件，已有文件不覆盖。保存完整 SSE、会话 ID、请求 ID、持久化一致性、逐轮耗时、模型配置名、代码与提示词摘要、数据前后校验状态。`tokens`、`cost` 尚未采集，值为 null。模型名来自本地配置，需确认正在运行的后端与配置一致；远程服务不在本工具范围内。运行期间应停止其他代码、数据、索引变更。

## 判分规则

自动检查与人工复核分开，避免一个混杂的“准确率”掩盖问题。

1. **协议与状态**：必须收到一个终态，类型符合题意；核对服务持久化的本轮问题与返回结果。要求先澄清或拒绝的题，若 SSE 显示进入 SQL 生成、校验或执行，则失败。SSE 没有该事件并不构成完整数据库审计证明。
2. **数据正确性**：比较数值与结果集合，不比较 SQL 字符串。按列含义和明确别名匹配，允许列顺序不同及额外列；不允许随意排列数值去凑答案。未知列名、转置布局交给人工映射。无顺序要求时保留重复行但忽略行顺序；要求排名展示时检查顺序。
3. **精度与空值**：计数、年份、月份精确匹配；金额与均值容差 0.01；百分数以百分数数值比较，容差 0.01 个百分点。NULL、0、空字符串含义不同。合理的空结果计入结果检查，不默认排除。百分数与比例单位不一致先复核；允许人工确认明确说明的万元单位、文字“无法计算”等等价表达。
4. **澄清内容**：只返回 `clarification` 不够，还要问对缺失的指标口径或比较基准。不能向用户要求数据库中不存在的退款数据后又假装已获得。
5. **分析质量**：逐项核对 rubric、引用数据、数字计算和结论；允许不同正确查询，不强制第一张表等于某一张参考表。检查“事实、可量化贡献、待验证原因”是否区分，不能把广告、库存、用户心理等猜测当成已验证原因。仅引用一个存在的证据 ID 不算证明。
6. **多轮质量**：核对每一轮的最终约束、是否正确取消旧条件、是否继承正确比较期；整个场景所有轮次正确才记为场景通过，不能只算最后一轮。

自动状态包括 `pass`、`fail`、`needs_review`、`not_run`。`pass` 只代表本轮自动检查通过，**不代表附带文字结论正确**。所有报告保留待人工复核标记；分析题和澄清题不会单凭类型匹配自动通过。因此在线报告的 `end_to_end_accuracy` 在复核前为 null。

建议保留原始报告，另存复核副本，为每一轮填写：

```json
{
  "status": "pass 或 fail 或 needs_review",
  "failure_category": "口径 / 时间窗口 / 召回 / SQL计算 / 澄清 / 证据 / 多轮状态 / 基础设施",
  "reason": "对应具体 rubric，说明哪些约束、数据或结论不符合",
  "evidence": "实际返回数据、SQL 或报告中的证据 ID",
  "automatic_override_reason": "如人工推翻自动结果，说明列映射、单位或等价布局原因"
}
```

正式成绩分别给出数据正确率、澄清/拒绝正确率、分析结论正确率、多轮整场成功率，以及各曝光标签下的结果。分母要写明已运行、跳过、基础设施失败及未复核数量；不能只从成功响应里计算。比较不同版本时保持同样数据、题目、预算和评审标准。

## 关于 SQL 修复分支

难题不保证触发语法修复：很多错误 SQL 仍能通过数据库校验，真正的错误在分母、范围和解释。18 个错误变体专门证明本集能发现这类问题。

需要稳定验证内部修复流程时，应在独立的故障注入测试里让第一次生成返回不存在字段或错误聚合，检查重试预算与重新校验，而不是修改真实数据来迫使模型出错。项目现有 `tests/` 已有 SQL 路由和校验分支测试；它们与本集的业务正确性评测是不同层次。
