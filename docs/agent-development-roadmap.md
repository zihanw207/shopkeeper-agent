# 电商问数 Agent：面向大模型应用开发岗位的改进路线

调研日期：2026-09-16。定位：基于开源教学项目的二次开发，目标是能展示、能解释设计取舍、能用实验验证改进的电商分析 Agent。

当前交付状态：第一阶段 SQL 执行闭环、关联键保留、自动化测试与 12 题评测入口已实现；操作与边界见 [评测说明](../evals/README.md)。第二阶段已实现多轮问题重写、结构化业务上下文、主动澄清、持久化会话与前端恢复，具体边界见 [多轮会话说明](conversations.md)；2 个场景共 5 轮真实模型验收通过。第三、第四阶段尚未实现；第五阶段已于 2026-09-19 先实现结果分析与有限补查，尚未通过真实模型效果验收。2026-09-16 经用户授权，以 DeepSeek 配置运行了前 3 道单轮真实链路测试及上述多轮验收；尚未运行完整测试集或改造前后对照，不能据此声称整体准确率或提升幅度。

## 2. 现有代码结构与实际边界

- `app/scripts/build_meta_knowledge.py` → `MetaKnowledgeService`：从数仓抽取表字段与值，构建 MySQL 元数据、Qdrant 字段/指标向量与 ES 值索引。
- `main.py` → API 路由、依赖组装 → `QueryService` → LangGraph：承接 HTTP 请求，执行工作流并产生 SSE。
- `app/agent/nodes/`：关键词抽取；三路召回；信息合并；表与指标过滤；补充日期与数据库环境；SQL 生成、校验、修正、执行。
- `app/repositories/`、`app/clients/`：数据访问与连接管理；`app/entities/`、`app/models/`：业务实体和存储映射。
- `prompts/`：检索扩展、上下文过滤、SQL 生成与修正提示词。
- `frontend/src/`：聊天样式 UI、流式消息解析、流程状态和结果表格；新增会话 ID、历史切换、刷新恢复和补全后的查询条件展示。不同会话的消息、草稿和请求连接分开管理，支持 A 执行期间切到 B 并行提问。
- `app/agent/conversation.py` / `app/repositories/conversation_store.py`：有限业务记忆、澄清决策和独立于单轮图状态的会话持久化。

底层查询仍是有条件分支的 Agentic Workflow。2026-09-19 新增结果分析外层循环，由模型阅读现有证据并选择 `query / finish`，最多补查两次；实现与验证边界见 [结果分析说明](result-analysis.md)。它还不能动态选择底层检索策略或任意工具。三路检索面向不同实体，不等于对同一候选集合做 BM25/向量融合与重排。

审阅发现的具体问题（改造前）：

1. `correct_sql` 直接连接 `run_sql`；修正后不再验证，执行报错也没有恢复分支。
2. DW Repository 直接执行模型 SQL；EXPLAIN 只能辅助检查可执行性，不能保证只读或业务正确。初始化脚本给应用用户的 DW 权限是 ALL PRIVILEGES。
3. `merge_retrieved_info` 补主外键，但后面的 `filter_table` 完全服从模型选择，可能再次删掉关联键。指标过滤与表过滤并行，后者看不到最终指标依赖。
4. 检索返回时丢弃分数，阈值与 top-k 固定；每个关键词的向量化和检索在分支内串行执行，分支间也可能重复向量化。
5. 元数据构建用普通 INSERT，重复运行可能主键冲突；Qdrant 使用随机 UUID，重复构建可能累积重复点。三个存储之间没有版本切换机制。
6. AOV 描述为平均订单金额，但 relevant_columns 指向 order_quantity；“平均单价”别名也混淆了商品单价和客单价。必须先固定业务定义，再评测。
7. request_id 日志与 SSE 进度已具备，但没有模型/提示词版本、token、节点耗时等可比较的实验记录；查询最终结果没有写回 State。
8. 缺少持久化会话、主动澄清、数据范围解释。示例数据只覆盖 2025 年 Q1，直接用今天解释“本月”很容易得到空结果。

## 3. 推荐推进顺序

### 第一阶段：可验证的 SQL 执行闭环

交付边界：校验→有限修正→重新校验→执行；不允许无限重试；区分可以修正的 SQL 错误和应当直接停止的服务/策略错误。增加 SQL 解析、表范围检查、返回行数限制和超时。用不依赖真实模型的测试验证分支，再用真实服务跑问数评测。

注意：SQL 解析不是数据库权限隔离。独立只读数据库账号、连接级只读事务、字段/行权限属于下一步部署加固，不能把应用层检查写成“已实现企业级数据安全”。

### 第二阶段：多轮上下文与主动澄清

目标演示：用户问“2025 年 Q1 华北销售额”，接着问“那华东呢”，能保留指标和时间，只替换地区；问“最近表现怎么样”时，先确认时间和指标。

已实现：会话 ID 与 SQLite 持久化；结构化保存指标、时间、维度和筛选条件；问题重写与 `clarify / query / unsupported` 路由；历史切换和刷新恢复。前端支持同一页面内多个会话并行执行、草稿隔离、后台新回复提示和只停止当前会话。成功查询摘要进入默认记忆，待澄清问题单独保留；失败 SQL 不进入下一轮上下文。同一会话通过事务串行执行，中断可释放占用，异常退出有租约回收。

实现取舍：当前澄清采用“保存会话 → 下一条消息重新进入理解模块”，未加入 LangGraph checkpoint/interrupt；恢复会话不代表从图中断节点继续执行。会话 ID 不是身份认证，部署时要校验会话所有权。

验证进度：会话相关后端测试 19 项通过，后端共 48 项测试通过；另有 11 项前端并发测试和浏览器模拟查询验收通过。使用 `deepseek-v4-flash` 的 2 个场景共 5 轮真实链路检查通过，覆盖地区条件继承、月份分组、会话隔离、澄清与补充，持久化重读一致。首次验收发现的强制工具选择兼容问题已改用 JSON 输出模式修复，失败与修复后报告均保留。后续目标仍是 20 组多轮对话，补充条件撤销、复杂指代及失败后重试等样本，测量条件继承正确率与澄清准确率。

### 第三阶段：Schema Linking 与业务语义层

目标演示：GMV、订单数、销量、AOV 使用一致口径；过滤后补齐指标依赖和 Join 路径；没有退款数据时明确说明不能算净收入。

实现：指标配置增加公式、粒度、过滤条件和时间口径；依据外键关系构建表连接图；在模型筛选后用确定性逻辑补依赖；把模型输出改成 Pydantic 结构化对象。AOV 在当前一行一订单的数据中可定义为 AVG(order_amount)，不等于金额除以件数。

验收：设计区分订单数与件数、订单地区与客户属性、多表重复计数的反例。SQL 能执行但指标错，仍判失败。

### 第四阶段：检索优化与性能实验

实现：保留候选分数和来源；对字段/指标引入词面匹配与向量检索，做 RRF 融合；按需加入 reranker；字段向量化批处理、请求内去重缓存与有界并发；给上下文设置 token 预算。

实验：同一冻结测试集，对比原始召回、融合召回、融合+重排；记录必需字段 Recall@k、最终执行结果正确率、p50/p95 延迟与每题模型调用/token 数。小表场景必须对比“提供完整 Schema”基线；五张表可能不足以证明复杂检索的收益。

### 第五阶段：有限工具选择与结果解释

2026-09-19 已先实现其中一部分：查询后的分析与有限补查，前端展示带证据的报告，失败和预算耗尽时保留数据并说明缺口。63 项后端与 14 项前端测试通过；本次使用模拟模型/查询验证工程行为，尚无新增真实模型效果成绩。第三阶段指标口径治理、第四阶段检索优化及下面的细粒度工具选择仍未完成。

在稳定工具层之上提供 `search_schema`、`get_metric_definition`、`validate_sql`、`execute_readonly_sql` 等有类型的工具。让模型根据观察选择补检索或修 SQL，并为调用次数、耗时、token 设置硬上限。对比固定工作流的成功率与成本，只有实验有收益再作为默认路径。

结果解释必须引用实际结果、时间范围和指标定义；空结果不能直接解释为“没有业务发生”。由查询结果生成趋势图与摘要时，要保留可核对的数据来源。MCP 可以作为工具复用接口扩展；接一个协议本身不能证明规划能力。

## 4. 评测怎么做才有简历价值

- 先从可人工审阅的小型种子集开始，逐步扩到 80–150 题。这是建设目标，不是已完成数量。
- 按单表、多表、聚合、时间、排序、指标口径、空结果、歧义、越界请求分层；训练/提示词样例与最终测试集分开，避免拿同义改写当独立泛化证据。
- 每题有参考 SQL、结果比较规则、必需表字段和分类。固定数据快照、模型与提示词版本。相对时间问题要固定基准日期。
- 核心指标是执行结果正确率；补充首次通过率、修复成功率、拒绝/澄清正确率、检索覆盖率、延迟、token 和成本。
- 保留行的重复次数；仅在题目没有排序要求时忽略行顺序；浮点比较使用声明的误差范围。禁止把“均返回空集合”作为充分正确性证据。
- 对价格未知的模型只记录 token，不编造人民币成本。失败样例要能定位到召回、口径、生成、执行或外部依赖。
- 单元测试通过率不是模型问数准确率；小规模 smoke test 也不等于可推广的 benchmark 成绩。

## 5. 面试时应该能拿出的材料

1. 架构图与决策记录：为什么固定流程起步，何时需要动态工具选择；为什么修正需要重验；何时应直接停止。
2. 可复跑评测命令、冻结数据和失败案例；基线与改进的对照表。
3. 三段演示：正常多表问数、SQL 修复过程、歧义澄清/越界拒绝。
4. 明确个人贡献与开源来源；指标只填写真实实验值，保留样本数、数据范围和版本。

可用的项目定位是“基于 LangGraph 的电商分析 Agent”。简历描述优先写“实现了哪些机制、解决什么具体问题、如何验证”。目前可以描述有限多轮业务记忆、主动澄清和会话持久化，并注明 2 个场景 5 轮真实验收；不能把它扩大为通用长时记忆或整体准确率。MCP、多智能体、图节点断点续跑和线上高并发尚未实现。
