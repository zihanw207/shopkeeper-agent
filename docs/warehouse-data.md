这些场景只规定可观测的数据变化，**没有设置或证明库存、流量、促销等业务原因**。比如华南平均订单金额下降，不能据此声称发生了打折促销。

## 原有结果与数据口径

2025 年第一季度全地区 GMV 仍为 **279,159.5**；华东 1—3 月销售额仍为 **54,924、17,508、34,941**。这些旧问题可继续做回归检查。

“全部时间”的合计会改变；2024 年已经有数据，旧评测中的 `empty_period`（2024 年 1 月无订单）也不再代表空结果场景。原有真实评测报告属于旧数据快照，不能直接拿数值与新版比较。现有 `evaluate_agent --check-fixture` 仍只读取原始 `docker/mysql/dw.sql`；验证新数据请用下面的扩充脚本。

2025 Q1 为保留的稀疏教学样例，新增时期为合成背景和受控场景。跨这两种数据密度计算同比能验证 SQL 运算，但不能把变化解释成真实经营趋势。完整日历也不等于业务采集完整。当前仍没有退款、支付状态、库存或流量表，金额列仍沿用原表的 FLOAT 类型。

AOV 元数据依赖/别名问题属于后续指标口径治理，本次没有修改指标库或重新生成索引。设计评测时应固定订单数、件数、已知金额平均值及完整客单价之间的区别。

## 可重现的生成与入库

生成逻辑在 `app/evaluation/warehouse_fixture.py`，固定随机种子为 `20260919`，不依赖当天日期。冻结清单为 `evals/fixtures/warehouse_extension_v1_manifest.json`，包含数据版本、行数及内容摘要。手工定义的 7 组场景参考 SQL 和预期结果在 `evals/datasets/warehouse_extension_v1_cases.json`。

在项目根目录执行：

```bash
# 离线生成并核验 7 组场景，不连接数据库
uv run python -m app.scripts.extend_warehouse --preview

# 只读核对当前本机 dw 和待追加记录
uv run python -m app.scripts.extend_warehouse --check

# 首次使用另一套原始教学库时追加；当前机器已经执行完成
uv run python -m app.scripts.extend_warehouse --apply

# 只读核验已入库数据与全部参考答案
uv run python -m app.scripts.extend_warehouse --verify

# 仅在 MySQL 已提交、ES 同步失败时补做季度索引同步
uv run python -m app.scripts.extend_warehouse --sync-values
```

脚本只允许本机 `dw`，要求原始记录与仓库种子一致；遇到额外或已修改的记录会停止，不会覆盖。使用事务、稳定主键与互斥锁；已有的相同数据跳过，提交前校验失败则回滚。重复执行不会新增第二份订单。原始初始化 SQL 含 DROP TABLE，本次追加使用独立脚本，**不需要重新初始化 MySQL 或删除 Docker 数据卷**。

首次入库前的备份（仅本地可读，已被 Git 忽略）：

`evals/reports/warehouse-extension-v1/20260919T032307754355Z/before.json`

入库与季度索引验证报告：

`evals/reports/warehouse-extension-v1/20260919T032307754355Z/report.json`

备份包含写入前五张表的数据。需要回退时，应根据该报告和 `EV1_` 主键范围制定有边界的回退操作，不重建整个数据卷。MySQL 和 Elasticsearch 是两套独立存储；脚本会明确报告“数据库已提交但季度同步失败”，此时单独重试 `--sync-values` 即可。
